## 1. 铁律（结构性，**不可配置**）

1. **引用豁免**：被**活跃 job**（`QUEUED/RUNNING/PAUSED`）引用的文件**永不删**——池/worker 直接 `pymupdf.open()`，删了就是运行中作业崩。
2. **永不自动删**：系统**没有任何自动删除路径**；API 启动时只**扫描＋记录/告警**（dry-run），**真删只能由人触发**。

## 2. 保留与淘汰（三个可配数值）

| # | 规则 | 默认值 | 一句话可改 |
| --- | --- | --- | --- |
| R1 | **保留期**：终态 job（`DONE/FAILED_PARTIAL`）引用的文件，自该 job 的 `updated_at` 起保留 N 天；**无 job 引用**的文件按文件 `mtime` 起算同样 N 天 | **30 天** | 7 / 90 |
| R2 | **容量闸**：inbox 总量超 M 时，按「**最久未引用**」淘汰到 0.8M（ACTIVE 豁免仍优先） | **50 GiB → 淘汰到 40 GiB** | 关掉 / 100 GiB |
| R3 | **两段式销毁**：先**移入 `inbox/.trash/<yyyymmdd>/`**（可回滚），在 trash 再留 T 天才**硬删** | **T ＝ 7 天** | 30 天 |

## 3. 可观测 / 可操作

- **CLI**：`python -m app.jobs_inbox gc [--dry-run|--apply]`（**默认 dry-run**：只列「将回收清单 ＋ 各文件体积 ＋ 可回收总量 ＋ 被豁免的文件及原因」）。
- **接口（additive）**：`GET /api/jobs/inbox/summary`（用量 / 将回收 / 豁免清单）；`POST /api/jobs/inbox/gc`（**默认 dry-run**，`{"apply": true}` 才真删）。
- **页面**：「新建 job」区下方一块 **inbox 用量**（文件数 / 体积 / 可回收）＋【预览清理】【执行清理】（**二次确认**，明示将删多少 GiB）。
- **报告**：每次 plan/run 落 `ops/job-upload/inbox_gc_<ts>.json`。

## 4. 为什么这样定（取舍说明）

- **为什么以「引用」而非纯时间为第一判据**：书的生命周期由 job 决定，不由文件时间决定；纯时间策略会删掉你正要重跑的书，纯引用策略则永不清（DONE 引用会永久钉住）⇒ **两者叠加**：ACTIVE 永久豁免（安全），终态按时间（可回收）。
- **为什么两段式 + dry-run 默认**：删的是**你拖进来的书**（最大单件 1.88 GiB，重传成本高）；软删 + 显式 apply 让「误判」变成可回滚的一步。
- **为什么不做常驻定时器**：本仓既有形态是「手动 + API 启动扫描」；常驻定时器引入新进程与新的失败面，收益不抵。
